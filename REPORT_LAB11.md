## 2. КОНЦЕПЦІЯ, UX-СТРУКТУРА ТА БІЗНЕС-ПРАВИЛА ВІДЖЕТА

### 2.1. Концепція віджета для платформи SimpleArduino
Для освітньої платформи SimpleArduino (освітній STEM-хаб з мікроконтролерної схемотехніки) було спроєктовано та впроваджено віджет: **«Інтерактивний калькулятор-конфігуратор інженерного набору SimpleArduino Starter Kit & Lab Stand»** (`#kit-configurator`).

Віджет дозволяє студентам, викладачам STEM-лабораторій та мейкерам:
1. Обирати необхідну кількість навчальних комплектів (від 1 до 50 шт.).
2. Вибирати рівень апаратної складності мікроконтролера (Базовий Uno R3, Середній Uno + LCD/Сенсори, Просунутий Uno + Робототехніка L298N/IoT).
3. Вибирати формат інженерної документації (Цифровий PDF, Друкований посібник ДСТУ, Ламіновані схеми А3).
4. Підключати додаткові апаратні опції (Li-ion автономне живлення, Антистатичний кейс, STEM-консультація викладача).
5. Обирати терміновість комплектації та логістику (Стандартна 3–5 днів або Експрес день-у-день).
6. Застосовувати промокоди зі знижками (`START2026` на 10%, `LP2026` на 15%) з повним захистом від XSS та бізнес-обмеженням максимальної знижки.

### 2.3. Математична формула обчислення
$$\text{CostPerKit} = \text{Price}_{\text{level}} + \text{Price}_{\text{guide}} + \sum \text{Price}_{\text{addons}}$$
$$\text{Subtotal} = \text{CostPerKit} \times \text{Quantity}$$
$$\text{BulkDiscount} = \text{Subtotal} \times \text{Rate}_{\text{bulk}} \quad (\text{де } \text{Rate}_{\text{bulk}} = 0.05 \text{ при } Q \ge 5; \; 0.10 \text{ при } Q \ge 10)$$
$$\text{PromoDiscount} = \text{Subtotal} \times \text{Rate}_{\text{promo}} \quad (\text{з урахуванням обмеження: } \text{Rate}_{\text{bulk}} + \text{Rate}_{\text{promo}} \le 0.25)$$
$$\text{Total} = \max\Big(0, \; (\text{Subtotal} - \text{BulkDiscount} - \text{PromoDiscount}) + \text{Price}_{\text{urgency}}\Big)$$

## 6. ВІДПОВІДІ НА КОНТРОЛЬНІ ЗАПИТАННЯ

### 1. Що таке інтерактивний віджет в контексті веброзробки? Наведіть приклади.
**Відповідь:** Інтерактивний віджет (Interactive Widget) — це автономний або напівізольований динамічний модуль веб-інтерфейсу, який приймає дані від користувача в реальному часі, обробляє їх за заданою математичною чи логічною моделлю в оперативній пам'яті браузера та миттєво оновлює стан DOM-дерева без повного перезавантаження сторінки.  
*Приклади:* Калькулятор вартості інженерного обладнання SimpleArduino Kit, конфігуратор ПК, кредитний калькулятор банку, інтерактивний конвертер валют, трекер калорій, віджет розрахунку вартості доставки.

### 2. Поясніть різницю між Happy Path та Edge Case.
**Відповідь:**
* **Happy Path («Щасливий шлях»):** Сценарій бездоганної експлуатації програми, за якого користувач вводить виключно коректні, передбачені бізнес-правилами дані (наприклад: 5 цілих наборів, дійсний промокод). Програма проходить базову обчислювальну гілку без відхилень.
* **Edge Case («Крайній випадок» / гранична ситуація):** Аномальна, нетипова або екстремальна ситуація, що виникає на межах або поза межами допустимого діапазону вхідних параметрів (порожній рядок, від'ємне число, нуль, дробове число, спецсимволи, астрономічне переповнення пам'яті чи шкідливий XSS-скрипт). Код повинен безпечно перехоплювати такі випадки, не допускаючи падіння застосунку.

### 3. Що таке Defensive Programming (захисне програмування)?
**Відповідь:** Захисне програмування (Defensive Programming) — це методологія та парадигма проєктування програмного забезпечення, за якої розробник виходить із припущення, що будь-які вхідні дані (від користувача, сторонніх API чи мережі) є за замовчуванням некоректними, пошкодженими або потенційно ворожими. Основна мета — зробити код настільки стійким, щоб він за жодних умов не видавав критичних помилок (Runtime Exceptions), не ламав інтерфейс (NaN / Infinity) і не призводив до фінансових збитків бізнесу, діючи за принципами Fail-Safe або Fail-Fast.

### 4. Які основні Edge Cases ви тестували в своєму віджеті? Назвіть мінімум 4 випадки.
**Відповідь:** У розробленому віджеті SimpleArduino Kit було протестовано 6 ключових Edge Cases:
1. *Порожнє поле (`""`):* перевірка на повне стирання значення з числового поля.
2. *Нульове та від'ємне значення (`0`, `-5`):* блокування введення некоректних кількостей.
3. *Астрономічне переповнення (`9999999999`):* захист від виходу чисел за межі типів даних та меж UI блоків.
4. *Дробові числа (`3.5`):* перевірка цілочисельності дискретних апаратних наборів.
5. *XSS-ін'єкція (`<script>alert()</script>`):* спроба впровадження скрипту в поле промокоду.
6. *Комерційне переповнення знижки:* захист від сумарної знижки >25% при поєднанні гурту та промокоду.

### 5. Що означає поява NaN в результаті розрахунку? Чому це виникає?
**Відповідь:** `NaN` (Not-a-Number — «не число») — це спеціальне значення числового типу (`typeof NaN === 'number'`) у JavaScript, що виникає, коли результат математичної операції є невизначеним або не може бути представлений числом.  
*Причина:* Виникає, коли JavaScript намагається виконати арифметичну операцію (множення, віднімання) над рядком, який не вдалося перетворити на число (наприклад, `parseFloat("") * 850` або `"abc" - 10`). У незахищеному коді `NaN` поширюється ланцюжком обчислень, призводячи до аварійного стану інтерфейсу.

### 6. Як ви захищали код від порожнього поля та від’ємних значень?
**Відповідь:** Захист реалізовано комбіновано на двох рівнях:
1. *Рівень розмітки HTML5:* Атрибути `min="1"`, `max="50"`, `required`.
2. *Рівень JavaScript (гварди валідації):*
   ```javascript
   const rawStr = String(rawValue).trim();
   if (rawStr === '') {
     return { valid: false, error: 'Поле не може бути порожнім.' };
   }
   const num = Number(rawStr);
   if (num <= 0) {
     return { valid: false, error: 'Кількість не може бути <= 0.' };
   }
   ```
   У разі спрацювання гварда функція негайно зупиняє подальший розрахунок (`return`), вмикає червону підсвітку інпуту та виводить зрозуміле повідомлення.

### 7. Яку роль має подія input та change при створенні інтерактивного віджета?
**Відповідь:**
* `input`: Спрацьовує миттєво в момент будь-якої зміни значення елемента користувачем (при кожному натисканні клавіші, вставці з буфера або кліку на стрілки інпуту). Це забезпечує реактивний UX — користувач одразу бачить зміну кошторису без додаткового натискання кнопки «Розрахувати».
* `change`: Спрацьовує тоді, коли елемент втрачає фокус після зміни, або безпосередньо при зміні стану випадаючих списків `<select>`, радіокнопок `<input type="radio">` та чекбоксів `<input type="checkbox">`.

### 9. Що потрібно робити, якщо в консолі з’являється помилка TypeError: Cannot read properties of null?
**Відповідь:** Ця помилка виникає, коли скрипт намагається звернутися до властивості або методу (наприклад, `.value`, `.addEventListener`, `.textContent`) об'єкта, який має значення `null` (тобто елемент не знайдено в DOM через помилку в селекторі `getElementById` або тому, що скрипт виконався до побудови дерева DOM).  
*Дії з усунення:*
1. Перевірити точність написання `id` в HTML та JS.
2. Огорнути виклик ініціалізації в слухач `DOMContentLoaded` або перенести `<script>` у кінець документа перед `</body>`.
3. Додати захисну перевірку існування елемента (Optional Chaining чи гвард):
   ```javascript
   const el = document.getElementById('my-id');
   if (!el) { console.warn('Елемент не знайдено'); return; }
   ```

### 11. Чому важливо обмежувати максимальне значення в полях (наприклад, max="50")?
**Відповідь:**
1. *Запобігання переповненню типів (Number Overflow):* Надвеликі числа (понад `Number.MAX_SAFE_INTEGER`, $2^{53}-1$) призводять до втрати точності арифметики або переходять у значення `Infinity`.
2. *Захист CSS-верстки (Layout Broken):* Числа з десятками знаків розривають межі текстових блоків, вилазять за межі карток і ламають мобільну адаптивність.
3. *Фізичний бізнес-сенс:* Утилітарний веб-віджет не призначений для розрахунку мільйонних промислових партій; оптові поставки мають окремі контракти, специфікації та логістику.

### 15. Які головні висновки ви зробили з цієї лабораторної роботи щодо якості коду?

## 7. ВИСНОВКИ

У ході виконання лабораторної роботи №11 було успішно закріплено практичні навички проєктування, реалізації та забезпечення якості інтерактивних веб-віджетів на чистому JavaScript (Vanilla JS).

Було сформовано вичерпний QA-план тестування та виявлено критичні вразливості первинного коду: поява `NaN`, від'ємні фінансові підсумки, переповнення буфера та потенційні XSS-загрози. Завдяки впровадженню гвардів нормалізації типів, обмеженню діапазонів чисел та переходу на безпечний рендеринг через `.textContent`, віджет досяг 100% стійкості. Автоматизований стрес-тест через Puppeteer у Chrome DevTools підтвердив повну відсутність критичних помилок (0 Page Errors, 0 Console Errors). Оновлену версію успішно задеплоєно на GitHub Pages.
